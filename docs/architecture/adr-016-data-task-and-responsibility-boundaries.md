# ADR-016：DataTask 协议与 AWE 职责边界

状态：已确认的架构约束；协议结构与验收场景是后续实现要求，不表示已有 DataTask API。适用基线：`main` 的 `0b6632b`。

本 ADR 进一步限定 [ADR-015](adr-015-domain-knowledge-and-controlled-consumption.md) 的任务入口、计划、轨迹和改进闭环；保留其成熟域推广顺序及 F0—F6 能力划分。今后的架构评审与新增能力设计必须检查本边界。

## 1. 首要定位

**AWE 是数据仓库面向 AI 和各类数据应用的统一语义、能力、约束与证据基础。AWE 让数据任务能够基于正式数据知识开展，不接管全部数据工作。**

业务语义、逻辑模型、合法计算及验证条件需要由系统正式承载，不能继续依赖各个 Agent 对文档和 Skill 的临场解释。与此同时，整体任务决策、协作和物理执行已有明确承载者，不应因此迁入 AWE。

| 层次 | 负责 | 交互边界 |
|---|---|---|
| 外部 Agent 与 Skills | 理解总体目标、拆解、选择工具、交互、代码编辑调试、分析推理、交付物和协作 | 按需要提出数据能力请求、候选引用或方案，消费结果与限制；决定后续工作 |
| AWE | Resolve 正式语义；Assess 能力边界；Plan/Validate 合法数据计算与加工约束；Evidence 来源、结果和验证范围 | 服务端解析、授权、校验并固定版本，提供受支持能力及自身调用证据；不接受调用方自行认证 |
| 既有工程与数据平台 | Hive/Spark/BI/指标计算，开发部署、调度、日志、质量及运行管理 | 执行已授权的平台操作，保留源端权限，提供实际制品、运行、数据状态和检查观测 |

AWE 可以通过注册适配器调用底层平台，也可以签发受控调用所需的范围明确、可复核的准入收据。后者必须由实际执行端验证主体、模型/计划/制品、策略、预算、有效期及必要的幂等或防重放条件；客户端拿到引用不等于拿到无限执行权。AWE 的服务端数据裁决不能退回为 Agent 自行阅读几份契约后宣告通过。

## 2. 四类场景使用同一基础，不建设四套 Agent 产品

| 外部场景 | AWE 提供 | Agent / 现有平台承担 |
|---|---|---|
| 数据开发 | 身份、来源、粒度、合法 Join、目标模型；受支持的类型化加工方案、契约与验收义务 | 需求沟通、开发步骤、代码生成编辑、调试循环、作业创建、发布协调与回滚 |
| 问数、取数与分析 | 正式口径、实体/关系、能力判断、合法计划、受控数据结果、统计前提与就绪/覆盖证据 | 分析策略、下钻选择、开放式推理、报告与用户交互；平台实际计算 |
| 值班诊断 | 作业与 Dataset 的绑定、数据状态、血缘/影响、质量证据及修复后的具名检查 | 接警、日志采集分析、故障假设、处置策略、重启/修复与事件管理 |
| 存量代码改造 | 输入输出契约、语义差异、影响范围、版本/制品绑定、回归义务和对账证据 | 代码理解与改写、Skill/SOP、性能调试、部署和业务交付验收 |

四张业务流程图说明的是外部工作的上下文，不意味着将整张流程图实现到 AWE。图示工时比例不作为已经验证的效率收益。开发、分析、值班和改造可以共用同一语义与证据基础；场景标签不成为通用任务路由或独立工作流引擎。

领域团队仍负责正式语义、规则和数据事实的确认与维护；平台团队负责共同基础及适配契约；Agent 团队负责自身任务完成。知识更新可以形成带来源的模型/规则候选，但从代码、日志或回答中抽出的含义不能自动成为正式业务事实。

## 3. DataTask 是轻量协议，不是工作流或第八类元模型

`DataTask` 表达一次可版本化的数据能力请求及其验证上下文。一个外部工作流可以调用零到多次 AWE 能力；调用顺序、任务 DAG、协作者、下一工具和交付进度由外部系统管理。AWE 自身的模型审核发布流程仍由 AWE 管理。

用户给出的 `ref / intent / requirements / consumer / entities / constraints` 是合适的概念起点，但不能把客户端提议与服务端已接受事实混在一个可任意修改的记录中。以下是逻辑边界，字段名和传输格式待实现时版本化，不提前宣称 Java 类型或 API 已交付：

| 部分 | 最少职责 | 信任边界 |
|---|---|---|
| 请求 | 协议版本；外部任务/步骤关联引用；所需数据能力；时间、身份、粒度、输出与质量要求；候选实体/计划；用途与请求预算 | 客户端输入均需检查，不能赋予权威、授权或通过状态 |
| AWE 接受上下文 | 自有操作引用；认证主体和有效委托；规范化要求；解析后的精确 Release/Hash；允许范围、策略版本和预算 | 由服务端认证、解析及授权产生；请求约束只能收紧适用策略，不能放宽 |
| 数据操作结果 | 语义与能力裁决、计划/Hash、执行与结果引用、具名证据、限制及缺口候选 | 可保留自身状态；只说明本次数据能力及验证义务的结果 |

特别约束：

- 不支持的协议版本，以及可能影响语义、权限或预算的未知要求/约束必须明确拒绝或要求重新提交，不能静默忽略后执行。
- 请求中的实体应称 `proposedEntities` 或 `requestedEntityRefs`，不称 `resolvedEntities`。客户端提交合法 ID/Hash 或 `resolved=true` 也不能替代服务端读取、校验和版本固定。
- `ConsumerContext` 可提供应用、用途、外部流程/步骤及 Skill 版本等声明。真实主体、租户、委托、角色、审批和最终授权来自可信认证与策略渠道，不能由请求字段自授；源端继续鉴权。
- `ExternalTaskRef` 是带来源命名空间的关联，不是 AWE 拥有的业务工单；AWE 自行产生 `OperationRef`。`PlanRef`、`EvidenceRef` 与平台 `RunRef` 可关联，但生命周期分开。关联引用不能跨租户或绕过对象访问校验。
- 模型发布版本、身份转换规则版本、实现制品版本、数据快照和协议版本分别记录，不能用一个 task version 替代。
- 调用方提交的日志、证据地址、`PASSED` 或外部完成声明只是待验证的报告。只有符合信任契约的来源与检查才能支持相应范围的 AWE 证据；外部引用不触发任意 URL 抓取或代码执行。
- 来源真实仍不等于适用本次请求。运行与验证收据必须匹配当前操作、平台 Run/尝试、相关模型/制品及数据时间范围，并检查策略要求的新鲜度；另一作业、旧重试或过期快照的真实成功不能替代当前证明。

意图限于数据语义相关能力，例如发现、解析、能力判断、查询、取数、加工方案校验、影响分析和数据验证。“开发并上线整套需求”“自主诊断所有故障”不是一个可由 AWE 接管的通用意图。

## 4. 数据计划可以组合，通用工具控制流不进入 AWE

| 计划或请求 | AWE 合法范围 | 外部职责 |
|---|---|---|
| QueryPlan | 固定语义、来源、参数、权限和预算的类型化数据算子组合；可由受支持编译器映射为 SQL/引擎请求 | 如何组织分析、继续追问或形成结论 |
| TransformationPlan / 加工意图 | 目标契约、输入输出、逻辑转换、增量/回补语义、依赖和验证义务；校验候选实现与版本/制品绑定 | 代码工程、开发调试、作业和部署生命周期 |
| 调查相关请求 | 查询指定数据状态、血缘、影响或证据，返回观测、限制及候选原因 | 选择假设、日志排障策略、工具循环和故障处置 |
| 变更相关请求 | 语义差异、兼容性、影响及所需回归；产生具名验证或准入收据 | 修改代码、安排测试/上线/回滚和跨系统协作 |

此前讨论中若将 `InvestigationPlan` 或 `ChangePlan` 理解为由 AWE 承担完整调查、修改和发布控制流，应按上表收窄；不新增通用调查或工程工作流管理器。

身份映射 → 合法 Join → 去重/窗口/比率，是受限的数据语义组合，可以属于 AWE。任意 Shell/Python 工具节点、Agent 反思、代码编辑循环、PPT 生成和部署协调不属于该计划。支持的数据代码实现只能经注册能力和明确约束使用，不能把自由代码节点包装成算子绕过边界。候选计划包含未知或越界节点时必须阻断，不能静默删除节点后按改变的意图执行。

对任意 Hive/Spark SQL、Python 或 Shell，不能承诺一般性的语义等价证明。必须区分受支持语法/算子的静态检查、具体契约的真实运行检查、样本或完整范围对账、独立业务验收；未解析部分、数据覆盖、容差与盲区必须保留。有限回归通过不证明任意代码、所有历史数据或全部未来输入等价。

## 5. AWE 只管理自身事实与有限状态

允许的状态包括：能力请求的解析/裁决/计划校验、受控调用的幂等/运行/证据、模型审核发布与验证、具名数据义务的技术缺口及重验。长查询可有平台 Run 引用、超时、取消和受支持的恢复机制；这不赋予 AWE 通用调度器职责。异步恢复只有实现并测试后才能宣称支持。

不管理消费者的完整任务 DAG、Agent 记忆/思考过程、任意工具历史、用户对话、代码工作区、故障处置手册或部署协调状态。追踪以 AWE 自身数据操作的最小必要意图、规范化要求、裁决依据和证据为限；外部步骤、日志和 Trace 使用受访问控制的引用关联，原始问题等输入按用途与保留策略处理，不复制整段聊天和全部执行日志。

必须区分：

1. 平台报告作业 `SUCCESS`：只说明相应平台的运行事实，不自动证明数据完整、正确或消费者任务完成。
2. AWE 具名义务 `PASSED`：只证明相应版本、范围、数据状态下的具体检查。
3. 技术 Gap `CLOSED`：只关闭满足原证明义务的该项技术问题，不关闭外部事件或所有下游问题。
4. 用户/领域负责人接受交付：由相应责任方决定。AWE 可保存带来源、范围与时间的 `ConsumerReportedOutcome`，不能将其冒称为自身证明的业务成功；收到一份回答也不自动构成验收。

缺口候选记录失败义务、模型/来源范围、证据及候选归因，必要时关联外部工单。归因、修复和验收按职责进行；不因召回未命中、Agent 判断或一次恢复就自动建知识、接管 ITSM 或完成全局结案。这样保留知识生产—使用—验证—改进的闭环，同时把实际修复和业务接受留给正确的责任方。

## 6. 四条设计红线

1. **复用既有平台。** 不建设通用 SQL 执行引擎、调度器、日志分析平台或代码工作区；注册执行适配和证据页面服务于明确的数据语义职责。
2. **不复制 Agent 编排。** AWE 可以拥有受控数据计划及自身调用状态，不能接管整体任务拆解、工具选择、交互和交付管理。
3. **领域扩展受治理。** 优先扩展正式领域模型、规则、类型化算子和 Adapter；公共内核不为每道问题硬编码专属流程。领域团队管理领域逻辑，版本、审核和反例约束同样适用。
4. **证明不越界。** 数据语义、计算合法性和质量只认证实际证明范围；开放式分析、总体业务成功及上线交付需要独立责任方验收。

## 7. 每次新增能力的评审门槛

新增模块或能力必须回答：

- 是否使真实资产的语义、关系或能力边界更明确？
- 是否使数据使用和开发遵循正式契约，减少散落 Prompt/Skill 硬逻辑？
- 是否使失败更容易定位，并形成可验证的知识或工程改进？

三项都没有明确收益的能力，应归外部 Agent 或现有平台。至少说明具体收益及验证方式，不以“AI 原生”作为独立理由。

设计/PR 评审还应写清：真实数据问题和已发布依据；请求/结果与证据范围；谁决定、谁执行、谁验收；权限、版本及失效条件；外部责任和非目标；失败/越权/未配置反例。检查 [B01—B10 边界场景](scenario-matrix.md#datatask-与职责边界验收b01b10)，不能仅凭正向演示通过评审。

## 8. 对路线与当前工程的影响

七类核心元模型和现有 Registry/发布/数据检查继续复用。DataTask 是运行协议，计划、调用记录与来源引用按职责建模，不为此增加第八类顶层本体。

M0→M1→M2→M3 保持不变：先成熟域资产，再可信消费，再本域新增变更准入，再复制。M1 优先把已可信的 BI/指标等实现注册为 DIRECT 能力，形成一次真实数据操作的解析、授权、执行、验证和证据链；不先建设完整任务管理、调查或代码改造系统。查询和加工共享语义，但可以有不同的数据计划与平台实现生命周期。

当前真实 PostgreSQL 只读检查仍只证明 [ADR-014](adr-014-agent-skills-and-data-verification-loop.md) 的三类义务；本 ADR 没有新增运行 API、引擎适配或企业验收结果。四类外部工作都需要公共基础，但不能据本设计宣称已经完成其中任何一类端到端业务交付。
