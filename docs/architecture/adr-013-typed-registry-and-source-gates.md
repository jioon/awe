# ADR-013：类型化发布边界、来源观测与兼容性 Gate

状态：已实现的 F1b 工程增量；真实企业来源接入和领域验收仍未完成。本 ADR 延续 ADR-002、003、008、009 和 012，不替代完整数仓生产、消费和修复闭环。

## 问题与基线审查

七类内核记录已存在，但原 F1a Registry 接收另一套宽松 JSON，允许缺少对象身份、特征可获得时间等强类型不变量。依赖只记录实体 ID，发布 Hash 只覆盖 `spec`，无法证明消费方使用哪个类型、版本和依赖内容。来源绑定允许作者填写任意指纹后以 `NOT_VERIFIED` 发布。

这使“类型已实现”“模型已审核”“物理来源已验证”之间存在断裂。继续叠加问数或 Agent 层会放大断裂，因此优先修复 Registry 的单一发布边界。

## 决策

### 1. 七类模型共享内核与发布表示

`schemaVersion: 2` 采用如下文档；`model` 直接对应 Java 内核记录，包含自身 `ref`，不另造隐式语义映射：

```json
{
  "schemaVersion": 2,
  "name": "用户",
  "definition": "由领域负责人确认的用户身份",
  "ownerTeam": "video_dw",
  "model": {
    "ref": {"id": "entity.video.user", "modelVersion": "1.0.0"},
    "family": "BUSINESS_ENTITY",
    "description": "注册用户类型",
    "properties": [{"name": "user_id", "type": "STRING", "required": true, "sensitive": false}],
    "identityKeys": ["user_id"]
  }
}
```

`entityType` 是 `ObjectType`、`LinkType`、`Dataset`、`Metric`、`Feature`、`FunctionDefinition`、`ActionDefinition`、`ContractDefinition` 或 `EvidenceAssertion`。其中后三种语义模型属于同一个 `SemanticModel` 家族，因此仍然是七类元模型。

未知字段、错误标量类型、缺少必填记录字段、重复集合成员和内核不变量失败均拒绝；不把未支持语义隐藏在扩展 JSON 中。集合采用确定性排序；记录列表保留有意义顺序。作者可以保存未完成草稿，但提交与发布必须经过相同的严格边界。

旧发布文档、Hash 和审核历史保留不变，读取不改写。旧草稿需作者明确补全 v2 文档后提交；系统不得推测身份键、时间或聚合含义，不能从“旧版本能保存”推断它能通过新 Gate。

### 2. 不可变发布与依赖版本

发布版本必须与 `model.ref.modelVersion` 一致。发布内容 Hash 绑定领域、实体 ID、类型、版本、Schema、规范化模型，以及规范化的依赖与来源清单；依赖清单记录精确模型版本、Release ID 和内容 Hash，来源清单记录系统、资产、版本、指纹、快照 ID 与直接/继承关系。未知版本、错误目标模型家族和自身依赖拒绝。

兼容性判断采取保守策略：对象身份、属性删除/类型变更/必填收紧，以及粒度、时间、计算语义、关系和能力契约的破坏性变化，需要提高主版本。版本不能回退，也不能通过更换模型类型绕过历史兼容性检查。提高主版本只表示作者接受破坏性演进，不证明下游已经迁移；仍需查看依赖影响并完成消费者验收。

### 3. 来源导入是观测，不是自动建模或证明

通过可扩展 `SourceAdapter` SPI 接入来源。首个实现读取运维配置的 Hive/BI 元数据 HTTP 网关，不接受请求方提供任意地址。网关需由现有元数据/BI 平台对接，不宣称已经实现 HiveServer2、Hive Metastore 或某个具体 BI 产品的原生驱动。

网关读取 `GET <base>/assets/<encodedExternalRef>`，返回显式的资产版本、列、声明粒度、时间字段和可选语义定义。服务端规范化并计算指纹，持久化不可变观测。语义来源绑定的 `timeFields` 将每个时间角色映射到实际列（例如 `{"EVENT_TIME":"event_time"}`），粒度目前按同名物理列映射。发布时重新读取来源，比较指纹以及模型所要求的粒度、时间与字段；无配置、访问失败、响应非法或漂移均不能变成验证成功。

`NOT_CONFIGURED` 只表示尚未配置，不表示企业不存在该资产。测试中的本地 HTTP 网关证明协议和 Gate 的真实执行路径，不等于连通了企业 Hive/BI。

BI 网关的 `definition` 必须映射为同一语义 `model` 的完整记录内容，移除根 `ref` 后与候选模型规范比较；缺失或不符会以 `CONTRACT_MISMATCH` 阻断，不能只对列或 SQL 文本相同就认定 BI 口径一致。Hive 元数据检查不提供这种 BI 声明语义等价。

证明范围必须随结果保留：列和声明粒度相同不能证明行级唯一性，元数据相同不能证明 BI 数值口径等价，快照匹配不能证明数据已就绪或业务事实绝对正确。

物理契约检查明确区分直接对象的属性/类型/可空性/身份检查，Dataset 的声明粒度与时间映射检查，以及 Metric/Feature 经精确 Dataset 版本继承的主体、字段、维度、时间和可获得时点检查。来源指纹的 `VERIFIED` 和候选模型的 `CONTRACT_MISMATCH` 可以同时成立。

原始来源观测和候选物理契约检查分别以独立事务追加，后者包含候选规范文档 Hash、身份、检查者、结果和细节；外层发布回滚不删除失败证明。查询接口为 `GET /api/validation-checks?entityId=...`。候选 Hash 不冒充带完整身份、版本和清单的最终发布 Hash。发布绑定中的历史验证时点和当前重新检查结果独立；重新检查不能修改发布 manifest。

### 4. Contract、Evidence 与来源检查分开

Contract 是有阶段和阻断性的义务；没有执行器支持的阻断规则或阶段必须失败关闭。初始发布规则为 `check.model.static` 和 `check.source.consistency`，只覆盖类型静态检查与来源一致性，不能把计划/执行/观察阶段的义务标记为已经执行。Function/Action 的断言引用使用 `assertion.<domain>.<name>@<version>`，解析到明确的 Evidence 发布，而非自由文本许可。

Evidence 是绑定目标发布 Hash 和来源快照的声明。提交 `PASSED` 或填写一个 URL 不会自动认证来源、授予执行权限或代替服务器产生的来源检查。未知目标 Hash、快照或不相符的证明范围不能作为发布证明。来源范围沿精确的 `sourceDataset`、Contract `subject`、Function/Action `ownerType` 实现链检查，不沿任意 `dependsOn` 扩大证据；实现链遍历有深度/节点限制。

Function 和 Action 本轮可建模、校验和发布；它们仍是声明。发布 Action 不会执行回补或重跑，`requiresApproval` 等声明也不能代替执行时的真实身份、审批、幂等、补偿和后验检查。

### 5. 漂移发现进入持久化问题记录

重新验证已发布绑定时保留每次检查，并将确定的漂移记录为带来源、模型版本和失败证明义务的缺口候选；展示依赖影响并去重开放问题。连接未配置或暂不可达不应被当成“数仓缺失”自动派生产工单。仅在同一绑定和契约的重新检查恢复期望指纹时，才可将该来源问题标记恢复；这不改写历史证据，也不宣称下游任务已回放或修复完成。

完整闭环还需：领域负责人确认归因 → 修改真实 SQL/DDL/任务或模型 → 正常审核发布 → 回放原任务和相关回归 → 验收关闭。当前没有真实任务执行器和回放机制，因此不宣称已完成这个闭环。

## 验收与尚未完成的生产门槛

必须通过 PostgreSQL Flyway 和真实 HTTP 集成测试，覆盖七类模型往返、精确引用、兼容性正反例、发布 Hash、角色隔离、未配置来源、观测导入、发布重读与漂移拒绝。不能用零测试或被跳过的集成测试代替验收。

仍需真实来源连接、业务领域模型和来源对账验收；企业身份、领域级授权、源端二次鉴权；受控数据任务消费发布模型；质量/数值/独立证据；修复与回放工作流。F1b 的可运行增量是达到这些门槛的基础，不是生产上线许可。

迁移采用新增表/字段，不修改既有发布。发布回滚使用已知旧应用与其不可变模型；已运行数据库不自动执行破坏性回滚，先评估新增文档能否由旧应用读取并备份。新版本修复通过新的迁移和模型发布前进，不重写旧证据。
