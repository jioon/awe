# 生产工程路线（不是实验性原型路线）

## 产品目标

数据团队通过正常的数仓开发流程交付正式的语义、计算、工程和验证契约。AWE 把这些契约编译为受控可用的数据能力，供 BI、算法、个人/平台 Agent 共享，并从实际任务中识别错误和缺口，推动数据模型与工程建设持续改进。

## F0–F6 阶段和可解决范围

| 阶段 | 工程内容 | 能解决的真实问题 | 退出标准 |
|---|---|---|---|
| F0 工程基础 | 完整架构约束；Java 核心类型/关系/时间/结果契约；Maven CI；测试矩阵 | 稳定边界，避免后续把 LLM/目录猜测误当正确性 | 契约测试与 CI 通过，ADR 经业务问题检验 |
| F1 模型生产 | PostgreSQL Registry、不可变版本、Authoring API、Web 编辑/审核、真实 Hive/BI/知识库源绑定、漂移检查 | 业务数仓团队可维护、发布一个真实模型，知道何为权威 | 一个真实领域端到端完成建模发布；可追溯审核和差异 |
| F2 受控问数 | Hybrid Resolver、候选消歧、Semantic IR/Compiler、BI 适配、MCP/REST、权限、证据 | 可信指标/维度查询、黑话、歧义正确澄清、非法查询拒绝 | 指标结果与权威 BI 对账；边界/权限负例全部通过 |
| F3 数仓闭环 | Dataset/Pipeline/血缘/质量、有限推导规划、变更兼容、在线评测和 Gap 工作流 | 现有数据能否推导、任务为何异常、加工变更影响谁 | 真实 DWD/DWS 变更可发现并验收；Gap 修复回放闭环 |
| F4 复杂分析 | 多跳 Join、桥接、扇出、SCD、比率/半可加、窗口、缓存/物化 | 复杂数仓的安全通用语义计算 | 每类复杂语义具代表性业务用例和非法反例 |
| F5 算法用数 | Profile/Feature、point-in-time、available-at、TTL、离线/在线/训练一致性 | 可查询历史可信特征并避免信息泄露 | 训练时点/回补/在线一致性测试通过 |
| F6 安全生产操作 | 任务/模型 Action、审批、幂等、回滚/补偿、后验证 | 安全回补、任务重跑、模型发布与恢复 | 完成授权安全审查、dry-run、失败恢复和审计 |

**F1 并非另做硬编码演示：必须真实连接内部资产来源并支持持久化与页面发布。**
F2 不接伪数据充当真实结果；外部系统尚未配置时必须明确 DISABLED / NOT_CONFIGURED。

## 刚开始应做的真实工程任务

1. 定义可版本化的 Typed Kernel，不绑定 Spring/LLM，约束时间/粒度/关联/能力。
2. Java 应用与 PostgreSQL Flyway 发布流水线，保证同一模型在建模和执行中一致。
3. 以现有 BI/Hive 数据为权威采集来源，建设首个 Domain Model 的 Source Binding 和 drift detector。
4. 提供 Web 的实体、关系、来源和验证视图，支持审核与发布；模型不能只在 YAML 和后台代码里。
5. 在 P1 的真实指标和 DWD 模型上做第一轮端到端不变量测试，再开放受控 Query/Resolver/MCP。

## 仍需同现有平台明确的接口问题

- BI 指标平台是否存储权威的粒度、聚合、维度、过滤与时间规则？只有 SQL 还是支持语义请求？
- 真实业务对象身份如何映射？用户/设备/游客、账号变更与历史版本是什么？
- 数仓数据的事件时间/服务端时间/分区/水位如何定义，哪些情况下数据可以回补？
- 现有血缘和 DDL/SQL 变化能否通过事件/接口获取？是否有源码版本？
- 数据权限在哪些系统判定？有哪些行列、PII、地域和跨域组合限制？
- 质量数据源与可用性/可信证据如何接入？接口失败时应如何回退？
- Query Budget、执行超时、并发、审计/脱敏等要求是什么？

首轮开发无需用户提供任何数据库密码；配置采用环境变量/密钥引用。正式实现不应把连接串写在仓库中。

## 每个增量的 Definition of Done

源码、自动化测试、正反案例、数据库迁移（如涉及）、观察与审计、接口契约、Web 可视化（如涉及）、文档、真实业务负责人验收及变更回滚方案。CI 绿是最低标准，不能代替业务任务验收。
