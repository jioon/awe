# AWE 产品目标、能力地图与逐域推广路线

## 产品目标与已确认路径

对外延续统一知识库，对内以 AWE 承载领域语义、能力裁决与受控数据使用。数据团队逐步交付业务实体、逻辑数据模型、加工意图、契约和能力；Hive/Spark/开发/调度/指标/BI 继续承担物理实现与运行职责。

**首要边界：AWE 提供统一语义、能力、约束与证据，不接管所有数据工作。** DataTask 是轻量、可版本化的数据能力请求与验证上下文；Agent 管理总体目标、流程、代码与交付，平台承担执行。AWE 管理自身调用及模型发布/验证状态，不能把调查、改造或发布协调扩展为通用工作流。具体约束见 [ADR-016](architecture/adr-016-data-task-and-responsibility-boundaries.md)。

推广顺序已经确定：**纳入成熟域已有资产 → 正确判断并完成该域支持的问数/取数 → 对本域新增与变更实施准入 → 再扩展成熟域**。先利用已有平台和知识，不要求从空白开始建模，也不要求先完成全部生产治理才能提供可信消费。

平台、业务和个人 Agent 都是下游。AWE 成熟后成为纳管域默认链路；现有 API/MCP 可作为受控执行适配器，自由 SQL/直接调用的例外兜底单独授权、追踪和统计。知识归集不等于计算正确，文档上下文也不自动授予执行权。系统必须能区分知识缺口、召回遗漏、语义歧义、计划错误、权限、数据/运行问题及 Agent 解释错误。

本次决策、目标架构、任务契约和迁移边界见 [ADR-015](architecture/adr-015-domain-knowledge-and-controlled-consumption.md)。目标成立以真实任务、可执行约束及独立验收为证，不以模块数量或测试数量替代。

具体工程增量、退出条件与当前首切面见 [实施路线](implementation-plan.md)。M1.1 先建设已发布 Dataset 的受控真实取数，M1.2 接入已有可信 BI/指标 DIRECT 能力，M1.3 按真实任务补齐通用语义与组合计算，再满足 M1 业务准入及 M2 实际生产发布约束；不建设完整任务管理或 Agent 编排平台。

## F0—F6 保留为能力地图，不作为串行交付清单

| 能力域 | 核心工程 | 真实验收问题 |
|---|---|---|
| F0 工程与语义内核 | 类型、身份、时间、粒度、版本、证据/信任边界、CI | 不同入口是否使用相同定义；错误与未支持语义能否明确拒绝 |
| F1 领域知识生产与发布 | 已有资产导入/映射、业务审核、统一知识库投影、Registry、版本、来源、覆盖声明 | 成熟域知识是否有负责人、权威、关系、时效与明确支持范围；不靠重复填报维护第二份真相 |
| F2 可信领域消费 | Resolver/消歧、完整计算与取数契约、Semantic IR、能力服务、BI/指标/Hive/Spark/MCP 适配、权限、预算、验证与阶段 Trace | 问数和取数是否正确完成；歧义/非法/未知/未就绪能否正确处理；失败能否定位发生阶段 |
| F3 数仓生产与改进闭环 | Dataset/Pipeline 实现意图、有界推导、可信作业/血缘/就绪观测、变更准入、传递与共享资产影响、在线 Gap/回归证据及外部验收关联 | 已有数据能否合法加工满足需求；真实失败推动哪一项知识/模型/数据/实现修复；新增变更是否受实际发布路径约束；不接管开发或运维工作流 |
| F4 复杂分析语义 | 多跳 Join、多对多、SCD、半可加、组合指标、物化 | 对域内所需复杂语义是否有明确规则和反例；不能用简单但错误的替代算法 |
| F5 算法用数 | Profile/Feature、point-in-time、可获得时间、离线/在线一致性 | 历史特征是否避免泄漏、回补混淆及训练/服务偏差 |
| F6 受控工程操作 | Action 执行、当前身份授权、审批、幂等、回补/重跑、补偿与后验证 | 是否可安全实施有副作用操作；失败恢复和审计是否真实有效 |

F2 的权限、预算、幂等、运行状态和基础验证不可推迟到 F4/F6；F3 归因与证据的一部分必须随可信消费交付。F4/F5 中域内任务必须具备的子能力按需提前，实现不了就缩小支持范围并明确拒绝。F6 的自主操作可以后置，F3 通过现有受审开发/部署流程落地真实加工不能全部后置。

F0—F3 的第一阶段目标是一个领域的知识生产、可信消费与数仓改进闭环，不代表任意复杂分析、算法场景和生产自动化都已支持。

## 实际交付与推广里程碑

| 里程碑 | 主要工作 | 退出标准 |
|---|---|---|
| M0 成熟域资产与任务基线 | 接入现有知识和平台资产，映射实体/指标/数据集/关系，梳理真实 SQL/MCP 取数路径，确认覆盖与验收集 | 领域负责人确认支持任务、权威、数据/权限边界、独立参考答案及更新责任；保留未知与冲突 |
| M1 成熟域可信消费，下一主要产品交付 | 知识发现与受控任务入口；直接能力及有界推导；正式问数/取数契约、源端授权、结果证据、可归因 Trace、问题修复回归；影子对账后切换默认入口 | 支持任务正确完成，歧义/拒绝/未知/未就绪处理正确；能区分召回、模型、计划、运行及解释问题；例外兜底单列，不能计入主链路达成 |
| M2 本域新增与变更准入 | 模型与实现制品绑定；传递/共享资产影响；候选版本及下游回归；现有开发/部署平台强制检查当前批准 | 实际发布不能用错制品、过期批准或改宽契约绕过；改进按原任务及受影响范围验收 |
| M3 下一成熟域与跨域治理 | 每域重复 M0→M1→M2；管理合法同名、共享定义、所有权和跨域权限/关联 | 每个域独立声明覆盖与达成；跨域能力经单独认证，不由单域成功自动推广 |

领域接入和平台实施由用户线下补齐；代码应提供完整适配契约、错误/未配置语义和可执行参考与测试。独立测试通过、参考平台可运行、适配器真实连通、领域业务验收、入口强制纳管必须分别报告。

## 当前代码基线与缺口

既有基线与 [ADR-017](architecture/adr-017-controlled-dataset-consumption.md) 的 M1.1 增量包含：

- F0：基础类型、七类元模型及正反测试。
- F1 部分：严格 v2 Registry、模型审核与不可变发布、版本/Hash/来源固定、Hive/BI 元数据网关与原生 PostgreSQL 观测、Web 工作台；成熟域覆盖声明与知识库投影尚未实现。
- F2 部分：DataTask v1 显式引用解析、独立消费策略、版本化 Dataset/输出行 Schema 驱动的真实 PostgreSQL 受控取数和证据；尚无完整自然语言 Resolver/Semantic IR、指标问数、真实用户委托或企业消费准入。Metric 当前字段仍不构成完整可执行计算定义。
- F3 部分：版本 Dataset/Contract 驱动真实 PostgreSQL 只读检查，保留失败与技术恢复记录。它证明三类受限义务的执行，不是语义问数、取数或生产作业闭环。Pipeline 尚为对象家族；影响查询主要是直接依赖；技术 CLOSED 不等于业务验收。
- F4/F5：有部分内核约束，未建立完整执行能力。
- F6：Action 可发布声明，未执行生产写入或自主修复。

既有基础应继续复用；不重新建立独立原型，不把后续目标写成当前功能。已实现边界见 [ADR-013](architecture/adr-013-typed-registry-and-source-gates.md)、[ADR-014](architecture/adr-014-agent-skills-and-data-verification-loop.md) 和 [ADR-017](architecture/adr-017-controlled-dataset-consumption.md)。

## 下一轮工程优先级

1. **先明确域与消费契约**：资产/权威/覆盖模型、正式问数与取数定义、版本化数据能力请求及其多维事实和阶段 Trace；分开客户端候选与服务端解析引用、用途声明与可信身份、外部任务与 AWE 操作。定义与知识库发现/文档投影的关系，不先建设通用任务中心。
2. **完成 M1 主链路**：优先把已有可信 BI/指标能力绑定为版本化 DIRECT 能力，再按任务需要补齐类型化计算与有界 Semantic IR；不先重写所有存量 SQL。补齐候选召回与消歧、受控执行适配、身份/权限/预算、独立结果验证和失败归因；同一内核映射 REST/MCP，不能仅开放现有 Registry 为“问数接口”。
3. **建立消费效果闭环**：真实任务/保留集/线上观测，区分发生点与根因；知识、召回、模型、数据/工具和 Agent 使用问题分别处理。AWE 复验相关数据操作并关联证据，外部责任方管理修复及业务验收；不接管完整调查、代码改造或 ITSM 流程。
4. **在已可用的域实施 M2**：正式 Pipeline 输入/输出/转换/制品，可信运行与数据就绪，影响与候选回归；绑定实际开发/部署准入。
5. **验证 M3 的可复制性**：把域特有语义留在域模型和受审算子中，公共内核保持稳定；避免业务 Skill 硬逻辑重新成为隐含权威。

问数接口、覆盖状态、Gap 工作流和身份策略若尚未实现，不能靠静态说明、人工宣告或无约束 LLM 回答充当其实现。

四类外部场景（开发、分析、值班、代码改造）是共同基础的验收视角，不是四套 AWE Agent 产品。每项新增能力必须说明对正式语义、契约使用或可验证改进的收益，并明确谁决定、谁执行、谁验收。QueryPlan/TransformationPlan 仅包含合法数据计算与加工约束，不包含任意工具、代码编辑或部署控制流。

## 验收与风险控制

每轮应交付真实可运行链路、正反例、版本/观测/审计、必要迁移、接口契约、用户可见状态、来源/语义/结果独立校验，以及业务负责人验收和回退办法。接口 fixture 证明协议实现，真实数据库测试证明相应执行范围，两者不能替代企业端的部署绑定和任务验收。

按 [任务矩阵](architecture/scenario-matrix.md) 中的 S01—S20、D01—D12 与 B01—B10 验收；M1 先覆盖所选域支持范围，不要求一次实现所有后续语义。支持覆盖、数据能力正确交付、正确澄清/拒绝、阶段归因、兜底、修复回归和维护成本分别衡量，阈值由业务基线确认。整体业务任务完成由外部责任方判定，作为带来源的反馈与数据证据分别统计。

优先控制：双份权威/重复录入、计算定义缺失、召回错误与知识缺口混同、元数据与实际质量混同、权限/知识外流、兜底绕过拒绝、不可恢复快照、域间口径冲突。不得用 CI 通过或代码规模替代这些验收。
